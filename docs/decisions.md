## 1. LLM 확신도 대신 YES/NO + 근거

- **문제**: LLM 이 내놓는 확신도는 보정되지 않은 자기 보고다. 임계값으로 쓰면 모델이나 프롬프트가 바뀔 때마다
  같은 숫자가 다른 뜻이 되고, 왜 그 점수인지 검토할 방법도 없다.
- **결정**: L3 는 도메인마다 YES/NO 와 근거 한 줄만 받는다. 근거 없는 YES 는 NO 로 본다. YES 가 하나면 SINGLE,
  수행·영업 둘 다면 PARALLEL, 하나도 없으면 되묻는다. 응답은 JSON 스키마로 검증하고, 끝내 실패하면 되묻는다.
- **대가**: 확신의 미세한 정도는 버린다. 대신 판정마다 사람이 읽을 수 있는 근거가 trace 에 남는다.
- **코드**: [`layer3.py`](../services/router/src/router_service/routing/layer3.py), [`judge.yaml`](../services/router/routing/judge.yaml)

## 2. 가중치 점수 대신 이진 규칙

- **문제**: 키워드마다 가중치를 주면 근거 없는 튜닝 값이 늘어나고, 결과가 바뀌어도 어느 값 때문인지 찾기 어렵다.
- **결정**: 레이어마다 결정 조건은 하나 — **"정확히 한 도메인"**. L1 의 exact / partial 은 매칭 전략이며,
  언어나 길이로 추정하지 않고 키워드가 YAML 의 어느 목록에 있느냐로만 정한다. 같은 키워드가 두 도메인에 있으면 시작을 거부한다.
- **대가**: 애매하면 결정하지 않고 다음 레이어로 넘기므로 LLM 호출이 일부 늘어난다.
- **코드**: [`layer1.py`](../services/router/src/router_service/routing/layer1.py), [`keywords.yaml`](../services/router/routing/keywords.yaml)

## 3. 레이어 격리와 입구 병합

- **문제**: 위 레이어의 점수를 아래로 넘기면 레이어를 떼어 낼 수 없고, 한 레이어의 실수가 다음 판단을 오염시킨다.
  멀티턴 맥락을 레이어마다 따로 주입하면 같은 질문이 레이어마다 다른 입력이 된다.
- **결정**: 레이어는 `route(query) → LayerResult` 하나만 노출하고 점수를 주고받지 않는다. 맥락은 캐스케이드 입구에서
  자기완결 질의로 **한 번** 병합하고, 모든 레이어가 그 질의를 받는다. 설정이 없는 레이어는 `skipped` 로 남겨
  "판단하지 못함"과 구분한다.
- **대가**: 레이어 간 정보를 섞는 최적화를 포기한다. 대신 어느 레이어든 빼고 돌려 기여도를 잴 수 있다(`eval --ablate`).
- **코드**: [`cascade.py`](../services/router/src/router_service/routing/cascade.py), [`contextualize.py`](../services/router/src/router_service/routing/contextualize.py)

## 4. 병렬(PARALLEL)은 L3 만 정한다

- **문제**: 키워드가 두 영역에 걸리면 두 갈래 질문으로 보기 쉽지만, 대부분은 단어가 모호한 경우다.
- **결정**: L1 · L2 는 여러 도메인이 걸리면 결정하지 않는다. "그리고 · 같이 · 둘 다" 같은 복합 질문 단서가 있어도 L1 은
  결정하지 않는다. 두 갈래인지는 문장을 읽는 L3 만 판단한다. 단서 목록은 넓게 잡는다 — 넓어서 틀리면 L3 호출이
  한 번 늘 뿐이고, 좁아서 틀리면 오답이 확정된다.
- **대가**: 병렬 질문은 항상 LLM 비용이 든다.

## 5. L2 임계값은 임베더별 값이고, dev 에서 정해 test 로 확인한다

- **문제**: 앵커를 바꿔 쓴 문장으로 정한 임계값은 실제 질문에서 통하지 않는다. 다른 임베딩 모델의 τ 를 그대로 쓰면
  오류 없이 조용히 오판한다. 시험셋에서 τ 를 고르면 시험 점수가 부풀려진다.
- **결정**: `thresholds.yaml` 에 τ 와 보정에 쓴 임베더 이름을 함께 둔다. 이름이 다르면 L2 를 건너뛴다(`skipped`).
  τ 는 골드셋 dev 분할에서 목표 정밀도를 만족하는 가장 작은 값으로 정하고 test 로 확인한다. 목표치와 측정치는 따로 적는다.
- **대가**: 임베더를 바꿀 때마다 다시 보정해야 한다. 이 레포의 해싱 임베더(fake)는 목표를 만족하는 τ 가 없어
  L2 를 끈 값(τ=1.0)을 기록했다 — 앵커 변형 문장으로 잡은 초기값은 실사용형 문장에서 정밀도 33% 였다.
- **코드**: [`layer2.py`](../services/router/src/router_service/routing/layer2.py) 의 `gate()`, [`run_eval.py`](../eval/run_eval.py) `calibrate-l2`

## 6. 되묻기는 지어낼 수 없게, 끝없이 반복되지 않게

- **문제**: 재질문 제안을 LLM 이 자유롭게 쓰면 없는 프로젝트 이름을 지어낼 수 있다. 되묻기가 이어지면 사용자가 빠져나오지 못한다.
- **결정**: 제안 속 프로젝트는 `{unit:P-101}` 자리표시자로만 쓰게 하고, 사용자 권한 목록과 대조해 이름으로 바꾼다.
  목록에 없으면 그 제안을 버리고, 남은 것이 없으면 고정 문구를 쓴다. 직전 턴도 되묻기였으면 제안 없이 영역 버튼만 준다.
  사용자 프로젝트 같은 추가 맥락은 **응답 생성에만** 쓰고 라우팅에는 넣지 않는다(결정 3).
- **대가**: 제안의 표현 자유도가 줄어든다.
- **코드**: [`hitl.py`](../services/router/src/router_service/runner/hitl.py)

## 7. 호스팅 에이전트 대신 직접 도구 호출 루프

- **문제**: 호스팅 에이전트 SDK 가 도구 함수를 프로세스 공용 상태로 다루면 동시 요청끼리 권한 값이 섞일 수 있고,
  thread · run 생명주기(생성 · 취소 · 삭제 · 재사용)를 관리하는 코드가 따라붙는다.
- **결정**: `ChatModel.complete(tools=…)` 로 무상태 루프를 돈다. 요청 컨텍스트(권한 · 예산 · 메모 캐시)는 도구 실행기에
  명시적 인자로만 넘긴다. 도구 스키마는 Pydantic 인자 모델에서 생성하고, 인자 검증 실패는 예외 대신 도구 결과로 돌려줘
  모델이 고쳐 부르게 한다. 라운드 · 호출 · 검색 수와 시간에 상한을 둔다.
- **대가**: 호스팅 쪽이 주던 내장 기능(웹검색 등)은 포트로 직접 붙여야 한다.
- **코드**: [`orchestrator.py`](../services/sales-agent/src/sales_agent/orchestrator.py), [`tools.py`](../services/sales-agent/src/sales_agent/tools.py)

## 8. 비대칭 서명 토큰과 서비스별 aud

- **문제**: 모든 서비스가 같은 HMAC 비밀을 쓰면 검증만 하는 서비스도 토큰을 만들 수 있다. `aud` 가 없으면 한 서비스용
  토큰을 다른 서비스에 들고 가도 통과한다. 개발용 로그인이 운영에 켜진 채 배포될 수 있다.
- **결정**: 라우터만 ES256 개인키로 발급하고, 나머지는 공개키로 검증만 한다. 사용자 토큰은 `aud=router`, 라우터는
  하위 호출마다 그 에이전트 전용 단기 토큰(`aud=<에이전트>`, 2분)을 새로 발급한다. 권한 범위는 토큰 클레임으로 실어
  에이전트가 DB 를 조회하지 않고 검색 필터를 만든다. 데모 로그인은 운영 설정에서 켜면 기동을 거부한다.
- **대가**: 키 배포 · 교체 절차가 필요하다.
- **코드**: [`auth.py`](../packages/core/src/chatcore/auth.py), [`settings.py`](../services/router/src/router_service/settings.py)

## 9. 대화 저장: 시작할 때 기록하고, 조건부로 끝낸다

- **문제**: 답변이 끝난 뒤에만 기록하면 끊긴 턴이 사라지고, 겹친 요청이 질문 · 답을 엇갈리게 저장한다.
  프로세스 메모리에 둔 대화 · 중지 상태는 재시작이나 다중 인스턴스에서 깨진다. 기억이 두 벌이면 서로 어긋난다.
- **결정**: 턴 시작 때 `pending` 을 쓰고, 대화당 진행 턴은 하나(DB 제약)다. 끝낼 때는 `pending` 일 때만 갱신한다.
  중지는 저장소 플래그, 끊김은 `disconnected` 로 기록한다. 대화 목록과 멀티턴 맥락이 같은 테이블을 읽는다.
  저장본의 연락처는 다시 가린다.
- **대가**: 같은 대화에서 두 질문을 동시에 보낼 수 없다(409).
- **코드**: [`store.py`](../services/router/src/router_service/store.py), [`runner.py`](../services/router/src/router_service/runner/runner.py)

## 10. 확장 질의는 검색에만, 관련도 판정은 원문으로

- **문제**: 용어사전으로 별칭을 덧붙인 질의로 리랭크하면 별칭이 관련도 판정을 흔든다.
- **결정**: 확장 질의는 BM25 · 벡터 검색의 재현율에만 쓰고, 리랭크는 사용자가 쓴 원문으로 한다. 모호한 용어(PO, PM)만
  LLM 으로 뜻을 고르고, 실패하면 확장하지 않는다. 확장 단계는 예외를 올리지 않는다.
- **대가**: 리랭커가 동의어를 직접 보지 못한다.
- **코드**: [`glossary.py`](../services/delivery-agent/src/delivery_agent/glossary.py), [`graph.py`](../services/delivery-agent/src/delivery_agent/graph.py)

## 11. 시간 예산은 턴 하나에 하나

- **문제**: 호출마다 타임아웃 · 재시도를 따로 두면 합계가 전체 기한을 넘고, 기한이 지난 작업이 뒤에서 계속 돌며 토큰을 쓴다.
- **결정**: 턴마다 `Deadline` 하나를 만들어 아래로 넘긴다. 각 호출의 타임아웃은 `min(자기 상한, 남은 예산)` 이고,
  `asyncio.timeout` 으로 실제로 취소한다. 단계마다 `child()` 상한을 둬 한 단계가 예산을 다 쓰지 못하게 한다.
- **대가**: 느린 앞 단계가 있으면 뒤 단계는 짧은 예산으로 돈다.
- **코드**: [`deadline.py`](../packages/core/src/chatcore/deadline.py)

## 12. 계약은 모델 하나에서

- **문제**: 에이전트마다 스트림 형식이 다르면 수퍼바이저에 정규화 어댑터가 쌓이고, 손으로 쓴 계약 문서는 코드와 어긋난다.
- **결정**: 이벤트를 Pydantic discriminated union 하나로 정의하고, 세 서비스가 모두 쓴다. SSE 직렬화는 HTTP 경계에서만 한다.
  웹의 TypeScript 타입과 [`api-contract.md`](api-contract.md) 는 이 모델의 JSON Schema 에서 생성한다.
- **대가**: 계약을 바꾸면 세 서비스와 웹을 함께 배포해야 한다(`SCHEMA_VERSION`).
- **코드**: [`events.py`](../packages/core/src/chatcore/events.py), [`export_contract.py`](../scripts/export_contract.py)
